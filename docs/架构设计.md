# 游戏语音视觉助手 · 架构设计

> 一个常驻桌面的悬浮球 / 桌宠。游戏里一句话唤醒，它"看见"屏幕、听懂问题、查攻略、开口回答。
> 目标机器：Windows + RTX 4060 Laptop 8G（显存紧张，本地只跑轻量模型，重活走云）。

---

## 1. 核心闭环

[热键/唤醒词] → 录音 → VAD断句 → 流式ASR ─┐
                                          ├→ 编排器 → 检索/工具 → LLM → 流式TTS → 说话
[触发瞬间抓一帧] → OCR 提取文本 ──────────┘                     └→ 卡片(详细答案+来源)

一次交互同时产出两样东西：**一段 5~8 秒的口语回答** + **一张可扫读的图文卡片**。
只做语音，长攻略念不完；只做卡片，游戏里没手点。两者缺一不可。

---

## 2. 三条设计主线

| 主线 | 原则 | 反例（很多项目死在这） |
|---|---|---|
| **低延迟** | 全链路流式，说完 1.5s 内出声 | 录完整段 → 整段识别 → 等完整回答 → 再合成语音 |
| **可打断** | 用户一开口，立刻闭嘴 | 播报中无法插话，只能等它说完 |
| **不干扰** | 默认鼠标穿透、不抢焦点、不进任务栏 | 悬浮窗挡住游戏按钮，或抢走游戏焦点导致人物乱跑 |

---

## 3. 总体架构

┌───────────────────────────────────────────┐
│ UI 进程 (PySide6)                          │
│  · 悬浮球 / 桌宠（透明·置顶·穿透）          │
│  · 气泡字幕 · 详情卡片 · 设置面板           │
│  · 只做渲染，不跑任何模型                   │
└──────────────────┬────────────────────────┘
                   │ 本地 WebSocket (127.0.0.1)
┌──────────────────▼────────────────────────┐
│ Core 进程 (asyncio Orchestrator)           │
│  · 状态机 IDLE/LISTEN/THINK/SPEAK          │
│  · 会话记忆、意图路由、工具调度             │
└───┬────────┬──────────┬──────────┬────────┘
    │        │          │          │
  ASR     Vision      Know        TTS
 (本地)   (抓帧+OCR   (RAG/搜索)   (云/本地)
          +云VLM)

**为什么一开始就拆两个进程**：Qt 事件循环和 asyncio 混在一个线程里（qasync）在加载 whisper / 播放音频时会互相卡死；模型 OOM 崩溃还会把悬浮球一起带走。拆开后 UI 永远是活的，core 崩了自动重启即可。成本只是几十行 WebSocket，收益是后面所有迭代都变简单。

## 4. 模块选型

### 4.1 悬浮球 / 桌宠

| 项 | 选择 | 说明 |
|---|---|---|
| 窗口 | PySide6：FramelessWindowHint + WindowStaysOnTopHint + Tool + WA_TranslucentBackground | Tool 让它不进任务栏 / 不出现在 Alt-Tab |
| 鼠标穿透 | Qt.WindowTransparentForInput，运行时可开关 | 平时穿透不挡游戏点击，按 F9 临时接管交互 |
| 置顶 | WS_EX_TOPMOST + 定期 SetWindowPos 抢最前 | 有些游戏和全屏优化会把置顶窗口压下去 |
| 状态表达 | 呼吸 → 聆听波纹 → 思考转圈 → 说话口型 | **这才是"我知道它在运行"的关键**，比状态文字有效得多 |
| 形象 | MVP：QPainter 自绘圆球 / 小精灵；进阶：序列帧、APNG | Live2D 的 Python 绑定（live2d-py）生态不成熟、坑多；真要做 Live2D，建议前端换 Tauri/Electron + pixi-live2d-display |
| 唇形 | TTS 播放的 RMS 包络驱动嘴部缩放 | 十来行代码，效果够用 |

### 4.2 音频

| 环节 | 选择 | 备注 |
|---|---|---|
| 采集 | sounddevice（PortAudio/WASAPI）16k 单声道 | 想听游戏内 NPC 语音，再加 WASAPI loopback（soundcard 库） |
| VAD | Silero VAD v5（ONNX） | 约 2MB，CPU 每 30ms 帧 <1ms，比 webrtcvad 准一个量级 |
| 唤醒 | **优先全局热键**（RegisterHotKey：F8 / CapsLock / 鼠标侧键），唤醒词可选 | 玩游戏时手本来就在键鼠上，"按一下说话"远比"喊唤醒词"自然；唤醒词可用 openWakeWord 自训练 |
| ASR | 中文首选 FunASR Paraformer-streaming；faster-whisper large-v3-turbo(int8) 兜底 | 关键：**内置游戏术语热词表**（BOSS 名 / 装备名 / 地名），准确率提升非常明显，别省这一步 |
| 回声消除 | **MVP 直接要求戴耳机** | WebRTC AEC 的 Python 绑定很折磨，先绕过 |
| 打断 | VAD 检测到人声 → 立即停止播放 + 清空 TTS 队列 | 打断是体验分水岭 |
### 4.3 视觉（重点）

**不要每帧喂大模型。** 两级流水线：

1. **抓帧**：mss（无边框窗口下稳定，单帧 20~50ms）；追求更低延迟可换 dxcam
   - 只在触发瞬间抓 1 帧，不做常驻 60fps 循环（那是白烧 GPU）
   - 压到 1280 宽 / JPEG q82，一张约 70~150KB，最多算 1024 token
2. **模型理解**：`deepseek-flash` 原生支持图片输入（image_url 块）
   - 它同时是"看图的眼睛"和"答问题的脑子"，不用两套模型对接
   - 每张图最多 1024 token，成本几乎可以忽略

3. **OCR 兜底（第 3 周再加）**：RapidOCR（PP-OCRv5 ONNX，纯 CPU 200~400ms）
   - 游戏小字、任务名、装备属性这类**精确字符串**，VLM 偶尔读错，OCR 是保险
   - 顺带能把文字直接拿去做检索，比让模型猜更准

### 4.4 攻略知识

| 层 | 做法 |
|---|---|
| 联网检索 | DeepSeek 官方 Search 接口（`POST /v1/tools/search`，返回 summary 600~800 字 + authority 权威分），命中不够再 `/v1/tools/fetch` 抓全文 |
| Agent 循环 | 模型自己决定搜不搜 → 出查询词（带游戏名）→ 拿回 3~5 条 → 生成答案 + 来源 |
| 本地 RAG（可选） | 常玩的游戏把 wiki 爬进 Chroma + bge-m3，省搜索次数、离线可用 |

**铁律**：通用大模型答游戏攻略幻觉极重，必须检索，且**一定要显示来源**，否则用户没法判断可信度。
DeepSeek 的搜索接口自带 `authority` 权威分（≥3 算极权威），排序时可以直接用。

### 4.5 一个 key 打通全部

既然选了 DeepSeek，就不需要多家供应商拼装了：

| 能力 | 接口 | 备注 |
|---|---|---|
| 看图 + 推理 | `POST /chat/completions`，`model=deepseek-flash` | 1M 上下文，支持 tool calls、JSON 输出 |
| 深度思考 | 同接口 `thinking: {type: enabled}` + `reasoning_effort` | 默认开，游戏助手场景建议关（慢 3~8 秒） |
| 联网搜索 | `POST /v1/tools/search` | ¥5/千次 |
| 读网页 | `POST /v1/tools/fetch` | 返回 Markdown |

客户端仍然按 OpenAI 兼容格式写，将来换别家只改 base_url。

### 4.6 悬浮球的"性格"

桌宠的可爱不靠美术资源，靠几个几十行能写完的小机制：

| 机制 | 做法 | 效果 |
|---|---|---|
| 眼神跟随 | 每帧取鼠标位置换算成方向向量，眼睛偏移 ±13% 半径 | 你动它就看你，最便宜的生命感 |
| 发呆瞟一眼 | 待机每 4~8 秒随机瞟 0.7~1.2 秒 | 不做这个，眼球会像死鱼一样定住 |
| 眨眼 | 4.6 秒一个周期，两段式闭合 | 单帧图片做不到的"活的"感觉 |
| 悬停放大 | `underMouse()` 驱动 0→1 插值，眼睛 +10%、球 +5% | 凑近它有反应 |
| 按下回弹 | 按下压到 0.93 倍，松手线性回弹 | 有重量感 |

状态用**颜色 + 眼睛形状**双编码（听=绿+睁大，想=黄+眯眼，说=紫+嘴型波形）。
只靠颜色对色弱不友好，只靠形状又太含蓄，两个一起才稳。

### 4.7 OCR 兜底（第 3 周）

模型看到的截图被压到 1280 宽，游戏里 15~20px 的小字（装备属性、任务名、BOSS 全名）会糊掉。
OCR 就是把这些**精确字符串**捞回来的手段 —— 尤其重要，因为攻略检索靠的就是准确的名字。

关键在于**不要让它挡在链路中间**：

```
按 F2 ─→ 开始录音 ─→ 同步抓一帧原图（0.14s）─→ 后台 OCR（~2s）
        │                                    │
        └──── 你说话 3~8 秒 ────┐            ┘
                                 ▼
                        识别完的文字 + 早抓的截图 → 发给模型
```

- 抓帧放在**按 F2 的瞬间**：这会儿气泡还没弹出来，截出来的画面是干净的（否则模型会看见自己上一轮的气泡）
- OCR 跑在后台，说完还没算完就直接跳过 —— 宁可少一份上下文，也不能多等
- 用了 RapidOCR（PP-OCR ONNX），**关掉方向分类器**（游戏字都是横排），2560×1600 一张约 2.2 秒

### 4.8 语音（第 2 周）

| 环节 | 做法 | 为什么 |
|---|---|---|
| 采集 | sounddevice 16k 单声道，30ms 一帧 | PortAudio 自带在 wheel 里，不用装驱动 |
| 断句 | 能量 VAD + 自适应噪声底，静音 780ms 自动结束 | 比"按住说话"自然；不用键盘钩子 |
| ASR | faster-whisper `small` int8，**CPU** | 显卡要留给游戏；3 秒语音约 1 秒出结果 |
| TTS | edge-tts（免费）+ miniaudio 解码 + sounddevice 播放 | 音色自然、流式、零成本 |
| 流水线 | 双线程：一个合成、一个播放，句子级并行 | 第一句在播时第二句已经在合成，句子之间不断档 |
| 打断 | generation 计数 + 静音标志 | 用户一开口，队列里过期的音频全部作废，不会"打完了还冒出一句" |

**两个坑**：

1. **不要用键盘钩子做"按住说话"**。低层钩子会被反作弊盯上，而 `RegisterHotKey` 拿不到 keyup。
   解法：点一下开始、静音自动停，语义上比按住更顺，实现上完全躲开钩子。
2. **国内下 HuggingFace 模型会挂**。新版 huggingface_hub 默认走 Xet 存储，镜像站不支持会 401。
   解法：先探测 huggingface.co 通不通，不通切 `hf-mirror.com`，并设 `HF_HUB_DISABLE_XET=1` 强制走普通 HTTP。

## 5. 延迟预算（说完到出声）

| 阶段 | 目标 | 手段 |
|---|---|---|
| 松手 → 首字 | 300ms | 流式 ASR，边说边出 |
| 首字 → 首个 token | 800ms | 检索并行发起；VLM 与检索同时跑 |
| 首 token → 首音频 | 300ms | Edge-TTS 流式合成，边收边播 |
| **合计** | **约 1.4s** | 超过 3s，用户就不想用了 |

## 6. 状态机

IDLE ──热键──▶ LISTENING ──VAD静音700ms──▶ THINKING ──首token──▶ SPEAKING
  ▲                 │                          │                    │
  └──── 超时/取消 ───┴──────────────────────────┴────用户开口────────┘

- 任何状态按 Esc → 立刻回 IDLE 并停止播放
- 播报中检测到人声 → 截断 SPEAKING 回 LISTENING（barge-in）

## 7. 输出双通道（很重要的产品细节）

让 LLM 输出结构化 JSON，而不是一大段 markdown：

~~~json
{
  "speak": "这个BOSS弱雷，二阶段会召小怪，先用范围技能清场。",
  "card": {
    "title": "深渊使徒 · 打法",
    "steps": ["弱雷，雷系伤害+50%", "二阶段召唤使徒，优先清小怪", "护盾阶段用大剑破"],
    "sources": ["https://wiki.biligame.com/..."]
  }
}
~~~

- speak：口语化、≤3 句、不带 markdown / emoji / 括号动作（TTS 念不了这些）
- card：结构化、来源可点
- 这样"念要点、看细节"的分工才成立

## 8. 全屏叠加的三个现实

1. **独占全屏（Exclusive Fullscreen）下，任何普通窗口都盖不上去** —— 这是 DWM 的设计，改不了。
   → 对策：引导用户把游戏设为「无边框窗口 / 窗口化全屏」。这是唯一稳妥解。
2. **独占全屏下 DXGI 抓屏可能出黑帧** → 同上，无边框就没问题。
3. **注入式 overlay（DLL hook + D3D/ImGui）能盖住一切，但会被反作弊当外挂** → 不要做。

**反作弊红线**：只读截屏 + 麦克风一般安全；**不要注入、不要 hook、不要模拟键鼠**。
腾讯 ACE / 网易易盾 / 米哈游 mhyprot / Vanguard 对 overlay 特别敏感。
对这类游戏，更安全的替代方案是：**手机或平板开个网页看卡片**（电脑跑服务、手机当第二屏），完全不碰游戏进程。

## 11. 风险清单

| 风险 | 判断 |
|---|---|
| 全屏叠加 | 最大的坑。第 1 周就要验证，别等 UI 做完了才发现盖不上去 |
| 语音打断 + 回声 | 第二大的坑。先靠耳机绕开，别一上来搞 AEC |
| 攻略幻觉 | 必须检索 + 显示来源，否则用户被误导一次就再也不用了 |
| 延迟 | 任何一环没流式化，整体体验就废 |
| 显存 | 8G 笔记本卡，游戏本身吃 6~7G，本地 7B 模型不现实，重活一律云 API |
| 成本 | 一次问答约 2000 输入 + 400 输出 token，¥1/¥4 每百万，一张图 1024 token 封顶；一天 50 次约 ¥0.2～0.5，可忽略 |
| 反作弊 | 竞技游戏（瓦罗兰特 / CS2 / 三角洲）建议直接不上 overlay，走手机第二屏 |

## 12. 打包

**单目录（onedir）+ 快捷方式，不做单文件。**

| 决策 | 原因 |
|---|---|
| onedir | 单文件每次启动都要把 900MB 解压到临时目录，冷启动十几秒；杀软也更容易误报 |
| 配置和模型放 exe 旁边 | 整个文件夹拷到别的机器就能用，不用重下 250MB 语音模型 |
| `--selftest` | 无控制台的 exe 出问题什么都看不到；自检写 `%TEMP%/gameassistant_selftest.log` |
| 图标 | 直接拿悬浮球渲染 256px 再转 ico，省得找美术 |

打包时容易漏的三样东西：

```python
collect_data_files("rapidocr_onnxruntime")   # det/rec/cls 的 onnx 模型
collect_data_files("faster_whisper")         # silero vad 权重
collect_dynamic_libs("ctranslate2")          # ctranslate2 的 dll
```

体积：程序约 467MB（Qt + onnxruntime + cv2 + ctranslate2），加模型共 931MB。

## 13. 配置与首次运行

**配置不落在"让用户改 json"上。** 一个设置窗分四页（AI / 语音 / 画面 / 快捷键），
保存后立刻生效，不用重启：

| 改动 | 生效方式 |
|---|---|
| Key / 模型 / 接口地址 | 丢掉旧 client，重建 Assistant |
| 快捷键 | 停掉旧监听线程，按新组合重新 `RegisterHotKey` |
| 音色 / 语速 | 直接改 `Speaker` 上的字段，下一句就变 |
| 球大小 | `setFixedSize` + 把中心点拉回屏幕内 |
| 识别模型 | 换新的 `WhisperASR`，下次说话时惰性加载 |

**首次运行**：没有 Key 且没打过 `welcome_done` 标记 → 900ms 后自动弹欢迎窗。
关掉（哪怕没填）就记下标记，不反复骚扰；之后靠气泡里的提示引导「右键 → 设置…」。

**快捷键录制**用一个只读 `QLineEdit` 子类，拦截 `keyPressEvent`：

```python
key = Qt.Key_F8 -> "F8";  Qt.Key_A -> "A"
mods = Ctrl/Alt/Shift/Win 依次拼在前面 -> "Ctrl+Alt+F8"
pure modifiers -> ""        # 单独按 Ctrl 不能录
Esc/Backspace/Delete -> 清空 # 否则 Esc 会把整个对话框关掉
```

录完的字符串直接喂给既有的 `parse_combo()` → `(mods, vk)` → `RegisterHotKey`，
和手写 json 走同一条路，不用维护两套解析。

## 14. 通话模式与对话记录

**唤醒词不做专用模型，复用已有的 whisper。**
常开麦克风 → 能量 VAD 切句 → 整句转文字 → 归一化后匹配唤醒词。
好处是不引新依赖、中文唤醒词随便起；代价是每句话都要跑一次识别（约 0.5~1.5 秒 CPU）。

三个细节决定了它能不能用：

1. **一句话说完就够**：命中唤醒词后，把词后面的内容直接当问题（"小助手，这 BOSS 怎么打" → "这 BOSS 怎么打"），
   不用先喊再等。只喊了词没带问题，才进入正常录音。
2. **自己说话不能被自己听见**：录音/思考/朗读期间 `enabled()` 返回 False，队列里的片段直接丢掉；
   开始录音前还会显式停掉唤醒监听，避免两个麦克风流抢设备。
3. **应答不能被自己录进去**：唤醒后先播「唤醒应答」再开麦，中间的等待用 `speaker.busy` 轮询（最多 4 秒兜底），
   否则"主人，我在"会被当成用户的问题。
4. **不能并发调模型**：唤醒线程和主线程都会调 whisper，`transcribe()` 里加了把锁。
   停旧监听时也不阻塞 UI —— 记下 `_wake_dying`，新监听等旧线程退干净（400ms 轮询）再开。

对话记录是追加写的 JSONL（`data/history.jsonl`），一条问答一行：
问一次写一次、翻的时候整文件读回来倒序。够简单，坏了也只坏一行。
